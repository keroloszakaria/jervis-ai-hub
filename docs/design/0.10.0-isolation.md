# 0.10.0: holding each CLI to its folder

Status: step 1 (Codex permission profiles, probe, fail closed) built in 0.10.0. The workspace copy is not built. Written 2026-11-07, after 0.9.11.

## What this fixes

Two gaps that `SECURITY.md` lists as known limits:

1. **Codex reads are not held to the folder.** Its `read-only` sandbox stops writes, not reads. A read-only Codex request can read any file your account can and send it to OpenAI. `ci/real-cli.ts` fails on this.
2. **No write is sealed.** Every write edits your real working tree, next to `.git`. The git guard locks refs through environment config, which an agent can undo. Antigravity's writes are not held to the folder at all; 0.9.11 turned them off for that reason.

The aim: a run can read and write only the folder it was given, enforced by the operating system wherever the hub can, and nothing reaches your real working tree until you have seen the diff.

## Threat model

The agent is the model plus the tools its CLI gives it. Assume it tries to read files outside its folder, write outside it, change git state, or forge the hub's records. The CLI itself (its binary and its sign-in) is trusted; the hub never reads its credentials. The machine's other programs are out of scope.

## What was checked on this machine

Windows 11 build 26200.9711, Codex CLI 0.167.0-alpha.3.2, Antigravity 1.5.3, OpenCode 2.1.4. Every result below came from a real run on 2026-11-07. Nothing here was checked on macOS or Linux.

### Codex permission profiles hold reads to the folder (MXC)

Codex has permission profiles (beta): named rules of `read`, `write` or `deny` per path, enforced by its OS sandbox. That is MXC or the legacy `elevated` sandbox on Windows, Seatbelt on macOS, and bubblewrap with seccomp on Linux (OpenAI's docs: learn.chatgpt.com/docs/permissions). They are set with `-c` for one run and must not be mixed with `--sandbox`, which the hub passes today; if both are present, the older setting wins.

The profiles below were tested with `codex sandbox` (commands only, no model) and then with `codex exec` through the real model:

```toml
# read-only
[permissions.hubread.filesystem]
":root" = "deny"
":minimal" = "read"
[permissions.hubread.filesystem.":workspace_roots"]
"." = "read"

# write
[permissions.hubwrite.filesystem]
":root" = "deny"
":minimal" = "read"
[permissions.hubwrite.filesystem.":workspace_roots"]
"." = "write"
```

With `-c windows.sandbox="mxc"`, `-c default_permissions="hubread"` (or `"hubwrite"`), and no `--sandbox`:

| Check | Built-in `:workspace` (control) | `hubread` | `hubwrite` |
| --- | --- | --- | --- |
| Read a file inside | works | works | works |
| Read a file under home, outside | **read it** | denied | denied |
| List home | works | denied | denied |
| Read or write the real temp folder by full path | not tried | denied | denied |
| Write inside | works | denied | works |
| Write outside | denied | not tried | denied |

Under MXC, `TEMP` points to a private temp folder for each sandbox, so a write to `%TEMP%` lands there and not in the real temp folder.

Through the real model (`codex exec`): with `hubread`, the read inside worked and the read outside came back "Access is denied", and the model said it could not get around it. With `hubwrite`, the write inside worked (a `file_change`) and the write outside was denied.

**The legacy `elevated` sandbox refuses these profiles:** "elevated Windows sandbox requires effective `:root` read access". It fails closed, which is right, but it means that on Windows only MXC can hold Codex's reads to the folder. MXC needs Windows 11 24H2 build 26100.9278 or 25H2 build 26200.9278 or later. `unelevated` does not support denied reads at all, and Codex refuses a policy it cannot enforce.

### Antigravity cannot sign in inside that sandbox

Antigravity run inside `codex sandbox` with MXC (its own folder readable, `~/.gemini` writable, network on) could not reach its sign-in. It started a new browser login and timed out. Making it work would mean handing its credentials into the sandbox, which the hub does not do. So the OS route is closed for Antigravity as it stands.

### Not checked yet

- OpenCode inside an OS sandbox: OpenCode's free tier hit its limit before the check could run.
- Codex's `apply_patch` aimed outside the folder under `hubwrite`: the model used the shell, which was denied. Patches must be checked on their own.
- macOS and Linux, for everything above.
- Network: these profiles leave the command network off. Codex's own model traffic is not a command, so it is not affected.

## Design

### 1. Codex: a permission profile on every run

- Read-only: `hubread`. Write: `hubwrite`. Both are passed with `-c` and need no change to `~/.codex/config.toml`. Drop `-s read-only` and `-s workspace-write`.
- Before the first run, and whenever the Codex version changes, run a probe through `codex sandbox` with the same profile: read a file in the folder (must work) and a file the hub puts outside (must be denied). Cache the result per Codex path and version, as `isolationProblem` does now.
- **Fail closed:** if the probe fails, or the platform cannot enforce the profile (`elevated` refuses it, `unelevated`, an older Windows build), the request is refused with the reason, and the Codex row in Diagnostics says so. A setting, "Allow Codex without read isolation" (off by default), brings back today's behaviour for people who choose it, and its question says so.
- `windows.sandbox="mxc"` is set for the run only, not saved in the user's config.

### 2. Writes go to a workspace copy, not the working tree

Every write (an `ask_ai` write, `delegate_ai`) runs in a copy:

1. **Copy:** the hub copies the folder's tracked and untracked files (git's list: `git ls-files -co --exclude-standard`, or every file outside a repository) into `~/.claude/jervis-ai-hub/work/<run>/tree`. It copies no `.git`, and nothing git ignores (`.env`, `node_modules`, build output). A folder over a size cap (say 200 MB or 20,000 files) is refused with the reason.
2. **Run:** the CLI runs in the copy, with its write profile (Codex) or its own rules (OpenCode). There is no `.git` in the copy, so the git guard becomes a second layer only.
3. **Diff:** the hub compares the copy with what it copied (content hashes), lists added, changed and deleted files, and keeps the diff.
4. **Review:** the diff is shown, as a summary for Claude and as files in the pane. Nothing touches the real tree yet.
5. **Apply:** only on your approval, and only if each file the run changed is still as it was when copied (otherwise those files are refused and named), the hub writes the changes into the real folder. It never commits.

This also solves the changed-file attribution issue (the list is the copy's changes, nobody else's) and makes a forged relay result harmless: the hub's diff is what counts.

### 3. OpenCode and Antigravity

- **OpenCode** keeps its own rules (file tools only, inside the folder; checked on 2.1.4), now inside the workspace copy. Next step: check it inside `codex sandbox` the same way. If its sign-in works there (an API key comes in its environment from the hub), OpenCode gets the OS layer too.
- **Antigravity** keeps its read-only `--settings` (checked on 1.5.3). Writes stay off by default. If you allow them, they run in the workspace copy, so the real tree is untouched until you apply, but nothing stops Antigravity from writing elsewhere on the disk. The setting's text says that.

### 4. Delegation through a relay

The relay gets the workspace copy as its folder. The hub keeps only its own diff of the copy and ignores the relay's account of what changed. Codex's relay runs with `--mode workspace-write`; whether the relay can pass a permission profile has to be found out. Until then a Codex delegation has the copy but not the read profile, and the answer says so.

### 5. The gate

`ci/real-cli.ts` gains:

- Codex with the profiles: read outside denied, write outside denied (shell and `apply_patch`), temp folder denied, read and write inside working.
- The probe's own check: on `elevated`, the run is refused (fail closed).
- The workspace copy: a run's change appears only after apply; an apply onto a file changed meanwhile is refused.

The Codex read check stays failed until the profile is in place, and a release that turns Codex isolation on must pass the gate on Windows.

## What it does not cover

- macOS and Linux are designed for but unchecked. The gate must run there before `SECURITY.md` says so.
- Codex on Windows without MXC: refused, or allowed without isolation by your choice. There is no third option.
- Antigravity: no OS boundary. Only its own settings, and the copy for writes.
- Network exfiltration through the CLI's own model traffic: whatever the agent reads inside the folder can reach its provider. That is what reading means.
- Branch protection on GitHub: a repository setting, outside the hub.

## Order of work

1. Codex profiles with the probe and fail-closed rules, plus gate checks. This closes the read gap on Windows with MXC.
2. The workspace copy for `ask_ai` writes, then for delegations.
3. OpenCode inside the OS sandbox, if its sign-in works there.
4. macOS and Linux runs of the gate, then `SECURITY.md` per system.

Steps 1 and 2 are each a release on their own: 0.10.0 and 0.10.1.
