# 0.10.2: writes go to a workspace copy

Status: built in 0.10.2, Keep for later included. Written 2026-11-07, after 0.10.1. The copy uses the folder's own `git ls-files` in a repository, which honours `.gitignore` files above a subfolder too. It details step 2 of `0.10.0-isolation.md`.

## What this fixes

Every write (an `ask_ai` write, `delegate_ai`) edits your real working tree, next to `.git`:

- The git guard locks refs through environment config, which an agent can undo. It is the only thing between the agent and `.git`.
- The changed-file list holds every change made while the run went on, by anyone.
- The agent can read every file in the folder, `.env` included, and send it to its provider.
- A change you did not want is already in your tree when you see it.

The aim: the agent works in a copy that has no `.git` and no secret files, and nothing reaches your folder until you have seen the changes and said yes.

## What the engine allows, and why the copy goes through git

- `$.fs.write` writes text only, and `$.fs.read` stops at 4 MiB. The hub cannot copy a binary file (an image, a font) through them, and it has no copy or delete call.
- So the hub copies, compares and applies with git, run with `$.process`. Git handles binary files, honours `.gitignore`, and is already required for the guard.
- The relay (`agy-delegate`) works in a folder with no git: its snapshot reads "not a repository" and goes on.

## Design

### 1. A git of the hub's own for each run

Each run gets `~/.claude/jervis-ai-hub/work/<run>/`, with `git/` (a bare repository the hub creates) and `tree/` (the copy). Every git command below runs with `GIT_DIR` set to that `git/`. Your own `.git` is never written: no objects, no index, no config. The git guard's environment is not set on these commands, since they are the hub's own.

### 2. Copy

1. `git add -A` with `GIT_WORK_TREE` set to your folder, into the hub's index. It takes tracked and untracked files and leaves out what `.gitignore` and `.git/info/exclude` leave out (`node_modules`, build output). Outside a repository it takes every file, minus the folder's own `.gitignore` if there is one.
2. **Left out even when git tracks them:** `.git`, `.env` and `.env.*`, `*.pem`, `*.key`, `*.p12`, `*.pfx`, `id_rsa*`, `id_ed25519*`, `.npmrc`, `.pypirc`, `.netrc`. They are passed as `:(exclude)` pathspecs. The answer names what was left out, so a build that needs one of them is not a surprise.
3. **Caps:** more than 20,000 files or 300 MB of content refuses the run with the reason. Nothing was sent.
4. A commit in the hub's repository records this as the base.
5. `git checkout-index -a` with `GIT_WORK_TREE` set to `tree/` writes the copy.

A link inside the folder is copied as a link (git's own handling), so it can lead out of the copy. Codex's profile still holds Codex to the copy. For OpenCode, a link that leads out is refused before the run (`git ls-files -s` mode `120000` pointing outside).

### 3. Run

The CLI runs in `tree/` exactly as it runs in the folder today:
- Codex under `hubwrite`, whose writable root is now the copy.
- OpenCode with its file tools only.
- Antigravity through the relay, if you allowed its writes.

The git guard stays on as a second layer, though there is no `.git` to guard. The prompt says the folder is a copy and changes are reviewed before they are applied.

### 4. Compare

`git add -A` with `GIT_WORK_TREE` set to `tree/`, then `git diff --cached --binary <base>`. This gives:
- the list of added, changed, deleted and renamed files;
- `git diff --stat`;
- the patch, saved as `work/<run>/changes.patch`.

The list is the run's own changes and nobody else's, so the "by anyone" note goes away.

### 5. Review and apply

After the run the hub asks you, as it asks before a write. The question names the folder, the number of files, the diffstat (the first 20 files) and the path of `changes.patch`. It has three answers:

- **Apply:** first, each file the patch touches must still be as it was at the base: the hub hashes your folder's file with `git hash-object` and compares it with the base. If any file changed since, nothing is applied, and the answer names those files. Otherwise `git apply --binary` with `GIT_WORK_TREE` set to your folder writes the changes. Nothing is committed or staged.
- **Keep for later:** the copy and the patch stay. A new tool, `apply_changes { run }`, asks the same question again later. Kept runs are listed in the pane's activity row and are removed after 7 days.
- **Discard:** the run's folder is removed.

Claude gets the diffstat and the answer. An apply never happens without your yes in that question. A "Yes" Claude writes in chat is not one.

A run with no changes asks nothing and says so.

### 6. Clean-up

The hub removes `work/<run>/` after Apply or Discard, and kept runs after 7 days, at session start. The engine has no delete call. Removal runs `rm -rf`, or `cmd /c rmdir /s /q` on Windows, and only on a path the hub resolved under `~/.claude/jervis-ai-hub/work/`, checked again just before it runs.

### 7. Settings

- **"Write straight into the folder"** (Privacy, off by default): today's behaviour, for a folder over the caps or a run that needs a left-out file. Its hint says the agent then edits your tree and `.git` directly.
- The caps and the left-out list are fixed in 0.10.2.

## Tests

Mocked tests:
- the copy's commands carry the hub's `GIT_DIR` and never your `.git`;
- the left-out pathspecs;
- the caps refuse with nothing sent;
- the CLI's cwd and `PWD` are the copy;
- the diff list;
- Apply writes nothing when a file changed since the base;
- Discard and Keep;
- no question when nothing changed.

Real tests:
- `ci/real-gitguard.ts` gains a real-git run of copy, change (binary file included), compare, apply, and an apply refused after a change to the original.
- `ci/real-cli.ts` gains a write in the copy for Codex: the change shows in the patch, and the real folder is untouched until apply.

## What it does not cover

- **A tracked secret with another name** (`config/prod.json`) is copied. The left-out list catches the usual names only.
- **Ignored files the build needs** (`node_modules`) are not in the copy, so a run that builds or tests may fail there. "Write straight into the folder" is the way out.
- **A link inside the folder** that leads out stays a link in the copy. Codex is held by its profile and OpenCode is refused, but Antigravity is not held by either.
- **macOS and Linux:** unchecked until the gate runs there.
